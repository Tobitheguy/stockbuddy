# CP2 Review — Signal Desk (independent cross-model review)

Reviewer model: Claude Sonnet 5 (independent of the model that authored CP2).
Scope reviewed: `src/db/schema.ts`, `drizzle/0000_watery_enchantress.sql`, `drizzle/meta/0000_snapshot.json`, `src/db/client.ts`, `drizzle.config.ts`, `scripts/seed.ts`, `src/config/source-seed.test.ts`, `package.json` db scripts. Base commit `a4e5f15` ("CP2: database schema, migration, seed"), preceded by `1af80f3`/`22feb75` (source list pruning). Since there is no live database, I built a real-Postgres verification rig instead of trusting a read-through: the actual PostgreSQL 17 C parser (`libpg-query`, WASM binding) to grammar-check the generated SQL, and an embedded real Postgres engine (`@electric-sql/pglite`) to actually *execute* the migration and run behavioral probes (constraint interactions, FK cascade behavior, `EXPLAIN` plans against synthetic data) that a static read cannot settle.

## Verdict

CP2 is a well-constructed, well-reasoned schema with genuinely good instincts — `numeric` everywhere money/prices could leak into a float, real Postgres CHECK constraints backing every Zod-validated range, `NULLS NOT DISTINCT` correctly reasoned through for the sector-signal dedupe case, a lazily-constructed DB client that won't break `next build`, and a seed script whose idempotence claims I verified line-by-line and by execution. `npm run build`, `typecheck`, `lint`, and `test` (23/23) all pass, `npx drizzle-kit generate` reports zero drift between `schema.ts` and the committed migration, and I confirmed the migration's SQL parses cleanly against the actual PostgreSQL 17 grammar and — going further than a syntax check — successfully applies to and executes against a real embedded Postgres engine (PGlite) from empty. But four of the review's target dimensions surfaced real, runtime-verified design defects rather than nitpicks. Most consequentially: the schema's own headline claim — "prices only ever contains trading-day rows, so +5 trading days is just the 5th following row" — is not actually protected by the schema in either direction. I proved by execution that (1) the `prices` primary key does nothing to stop two rows landing on the same calendar day if the ingester ever emits a timestamp that isn't exact UTC midnight (a retry, a timezone slip, a DST-adjacent bug), silently shifting every subsequent "+Nth row" offset for that symbol forever, and (2) there is no schema mechanism anywhere to distinguish a real non-trading day from a day the price backfill simply failed to fetch — both look identical (no row), so a bad API day silently corrupts the +1/+5/+20 outcome computation with nothing to catch it, on the one page (`/stats`) whose credibility the product is built around. Separately, I proved by execution that the `signals.symbol` `ON DELETE SET NULL` cannot do what its own comment and the commit message say it does: deleting a ticker that has any company-level signal (the common case, where `sector` is NULL) doesn't turn that signal into "a sector-level signal with no sector" — it throws a `signals_symbol_or_sector` CHECK violation and the DELETE fails outright, every time. And I proved by `EXPLAIN` that `signal_outcomes_pending_idx` — the index the schema comment explicitly says exists for "the outcomes job finding signals whose +1/+5/+20 prices are still null" — cannot serve that query at all: it indexes only `updated_at`, has no predicate on the null columns, so Postgres is forced to sequential-scan the whole table regardless of size. None of these break CP2's own stated deliverables today (nothing yet writes to `prices` or deletes a ticker), which is why I've rated them MAJOR rather than BLOCKER, but all four are cheap to fix now and expensive to discover after CP3/CP4 have built on top of them.

## 1. Schema correctness and data modelling

Went table by table (`src/db/schema.ts:73-415`). Money/prices are `numeric` everywhere without exception — `qualityWeight`, `marketCap`, `confidence`, `score`, `priceAtSignal`/`price1d`/`price5d`/`price20d`, `return*`, `close`, `priceAtAdd`, `llmCostUsd`, `costUsd` — I found zero `real`/`float`/`double precision` anywhere in the schema (grep-confirmed). NOT NULL placement looks deliberate and correct: e.g. `items.summary`/`bodyText` are nullable because they're genuinely optional (body only when `storeBody` is true), `tickers.exchange`/`sector`/`industry` nullable because the weekly ticker sync's source data may not always populate them, `signalOutcomes.price*`/`return*` nullable because they are "not yet known" by design (the comment at `schema.ts:296-300` is explicit and correct about this).

Two real, execution-verified defects surfaced (see findings table): the `signals.symbol` `ON DELETE SET NULL` / `signals_symbol_or_sector` CHECK interaction, and the free-text `sector` column's inconsistency with the enum treatment given to every other categorical column. Everything else — the six enums, the seven CHECK constraints, the `tickers_symbol_upper` uppercase guard, the `sources_poll_interval_positive` floor — checked out both by reading and by trying to violate them against a real engine (see §3).

## 2. The trading-day design

This is the most consequential section of the review because the design's core claim doesn't survive execution in either direction:

- **Half-days**: not a real risk. A shortened session still produces exactly one legitimate closing price for that calendar day, so "the 5th following row" logic is unaffected by session length. I don't think this needs a fix.
- **Duplicate/near-duplicate rows for one logical trading day**: a real, verified risk. `prices.ts` (`schema.ts:326`) is `timestamp with time zone`, and the PK is `(symbol, ts)` (`schema.ts:330`). I inserted two rows for `DUPTEST` at `2026-01-05T00:00:00.000Z` and `2026-01-05T00:00:00.001Z` — both succeeded, because to Postgres these are different `timestamptz` values, full stop. Nothing in the schema encodes "this column represents a date, not an instant" the way the comment (`schema.ts:325`) claims it should. A retried fetch, a timezone-handling bug, or an off-by-a-few-hours ingest mistake silently inserts a second "trading day" and permanently desyncs the offset arithmetic for that symbol from that point on.
- **Gaps from a failed backfill**: a real, verified risk, and one the review explicitly asked about. I simulated a fetch failure by skipping day 4 of a 9-day run — the resulting `prices` rows are indistinguishable from what a genuine market holiday would produce. There is no column, flag, or companion table anywhere that records "day 4 was expected and didn't arrive" versus "day 4 was never a trading day." The outcomes job (not yet built, CP4/CP5) has no way to detect this at read time either, since detecting it requires knowing the real trading calendar — precisely what this design set out to avoid needing. The minimal fix doesn't require maintaining a calendar for the offset arithmetic (that part of the design is fine); it requires a small amount of state for *anomaly detection only* — see the findings table for a concrete proposal.

## 3. Uniqueness and dedupe guarantees

Verified by execution against a real Postgres engine (PGlite), not just by reading the migration:

- **`items.canonical_url`**: unique index (`items_canonical_url_key`, migration:142). Re-inserting the same `canonical_url` correctly fails with `duplicate key value violates unique constraint "items_canonical_url_key"`.
- **`signals(item_id, symbol, sector)` with `NULLS NOT DISTINCT`**: verified two ways. Two sector-level signals for the same item with the same sector (`symbol=NULL, sector='Steel'`) correctly collide (`duplicate key value violates unique constraint "signals_item_symbol_sector_key"`) — confirming the `NULLS NOT DISTINCT` reasoning in the header comment is not just aspirational, it actually works. A second sector-level signal for the same item with a *different* sector (`sector='Utilities'`) correctly succeeds, confirming the constraint isn't overly broad either.
- **`story_key`** (`schema.ts:134-140`, index at `items_story_key_idx`): this is a non-unique btree index, and that's the right shape for its stated job — clustering multiple items that report the same underlying story so a future processor can look up "has anything with this story key already been scored?" before paying for a model call. It is not currently *used* by anything (no scanner/processor exists yet — that's explicitly CP3's job), so as of CP2 it is infrastructure without a consumer, not a bug. Worth flagging only as a "watch this" — the cost-saving story-clustering feature the header comment (`schema.ts:135-138`) calls "the single biggest cost lever in the system" doesn't exist yet and CP3 needs to actually query this index for the claim to become true.
- **CHECK constraints** (`signals_magnitude_range`, `signals_confidence_range`, `signals_score_range`, `tickers_symbol_upper`): all verified to actually reject bad writes at the database level (magnitude `0`, lowercase ticker symbol), not merely declared.

## 4. Indexes

Checked against all four named hot paths using `EXPLAIN` on a real engine with synthetic data (500 tickers, 3000 items/signals, 2000 llm_usage rows) rather than reading the index list and assuming it's aligned:

- **(a) processor's unprocessed-item queue** (`items_unprocessed_idx`, partial on `published_at WHERE processed_at IS NULL AND prefilter_reason IS NULL`): confirmed via `EXPLAIN` — `Index Scan using items_unprocessed_idx on items`. Correctly built and correctly used.
- **(b) dashboard signals by score DESC with ticker/event-type/time-window filters**: with a ticker+event-type filter, the planner combines `signals_symbol_idx` and `signals_event_type_idx` via `BitmapAnd` — reasonably effective even without a composite index. The unfiltered "top 20 by score" case chose a sequential scan + sort over `signals_score_idx` at this table's synthetic size (3000 rows); that's a normal, correct cost-based decision at low row counts, not a defect — the index exists and Postgres will switch to it once the table is large enough that the seq-scan cost exceeds the index-scan cost, which is exactly the tradeoff the planner is supposed to make. No composite index exists for the ticker+event-type+time-window combination; deferring that until CP5's actual dashboard query shapes exist is reasonable rather than premature-optimizing now.
- **(c) daily budget guard summing today's llm_usage cost** (`llm_usage_created_at_idx`): confirmed via `EXPLAIN` — `Bitmap Index Scan on llm_usage_created_at_idx / Index Cond: (created_at >= date_trunc('day', now()))`. Correctly built and correctly used.
- **(d) outcomes job finding signals with pending +1/+5/+20 prices**: **not supported**. See the MAJOR finding above — `signal_outcomes_pending_idx` indexes only `updated_at` and cannot serve a predicate on `price_5d`/`price_20d IS NULL`; confirmed via `EXPLAIN` to force a `Seq Scan` regardless of table size.
- One additional observation, not rated as a defect: `signals` doesn't denormalize `source_id` from `items`, so a future "hit rate by source" `/stats` query requires a join through `items` on every call. Fine at this scale; worth revisiting if that query is ever slow.

## 7. Security and operational risk

- **Neon client** (`src/db/client.ts`): warns but doesn't fail on a non-`-pooler` URL (`:26-35`). Reasonable: a direct connection genuinely works for local dev and low-concurrency use, and hard-failing would block a legitimate (if suboptimal) configuration. No connection string is ever logged — the warning message is static text, not string-interpolated with `url` — confirmed by reading the full function body.
- **Lazy client caching** (`cached ??= create()`, `:44-47`): safe under Node's single-threaded execution model. `create()` is fully synchronous (no `await` inside it), so there is no window between the `??=` check and assignment where a second concurrent call could observe a half-initialized `cached`. Not a real race condition.
- **`drizzle.config.ts` placeholder** (`:16-18`): safe failure mode in essentially all real scenarios — `migrate`/`push` would need to actually connect to `localhost:5432` with literal credentials `placeholder`/`placeholder`, which will fail authentication or connection against any real Postgres instance. Theoretical-only risk noted as a NIT above.

## 8. Gaps against the product

- **Story-level dedupe across sources**: scaffolding exists (`story_key` + index), enforcement is explicitly CP3's job. Not a gap at CP2.
- **Rule-based prefilter**: `items.prefilterReason` and `scanRuns.itemsPrefiltered` are both present and sufficient for CP3 to record and CP5 to display "what was filtered and why." No gap.
- **Prompt versioning for A/B on /stats**: `signals.promptVersion` (`schema.ts:232`) is present and sufficient to group hit-rate by prompt version at query time; no dedicated `prompts` table is needed for a single-user tool at this scale. No gap.
- **Live price chart on the ticker page**: `prices` stores one daily close per symbol per day — sufficient for a research tool's historical chart (not a trading terminal), and "live" current price can reasonably be fetched from the market-data API at render time rather than stored. If genuine intraday charting is ever wanted, this schema would need a new table (not a migration of `prices`, which should stay daily/canonical for the outcomes math) — worth knowing now, not urgent.
- **Watchlist return-since-added**: `priceAtAdd`/`priceAtAddAt`/`priceAtAddSource` are all present and correctly designed (nullable to make a failed/closed-market capture visible rather than silently wrong, per the header comment at `schema.ts:346-353`, which I verified matches the actual column definitions). No gap.
- The two structural gaps that *will* be expensive to retrofit later are the ones already covered above: the `prices.ts` duplicate-day risk (cheap to fix now as a column-type change; expensive once CP4/CP5 have written outcome-computation logic that assumes one row per day) and the missing gap-detection mechanism for backfill failures (same — cheap now, expensive once `/stats` has real history built on top of unflagged gaps).
