# CP0 Review — Signal Desk (independent cross-model review)

Reviewer model: Claude Sonnet 5 (independent of the model that authored CP0, which per the commit trailer was Claude Opus 5).
Scope reviewed: commit `b0f2e43` "CP0: scaffold Signal Desk, env template, verified source seed, fixtures" on `main`.

## Verdict

CP0 is in good shape and does not overreach its stated scope: no database schema, no API routes, no LLM calls, and no dashboard UI were built — `src/app/page.tsx` is still the untouched `create-next-app` template, which is correct at this checkpoint. Secret hygiene is solid (verified concretely with `git check-ignore`, a live `.env.local` probe, and a full-history grep — no secret ever entered the repo, `.env.example` contains only placeholders, and no `NEXT_PUBLIC_`-prefixed variable exists). `npm run build`, `typecheck`, and `lint` all pass cleanly, and all four raw fixture files are well-formed XML/JSON. The two spot-checked "money" claims in the README — Vercel Hobby cron being once-daily-only vs. Pro's per-minute cadence, and Finnhub's 60 req/min free tier vs. Polygon's ~5 req/min — are both independently confirmed correct via web search, so the Vercel Pro recommendation is not built on a wrong premise. That said, the checkpoint has real quality gaps that should be fixed before relying on it: PROGRESS.md/README misstate the fixture eval-assertion count (claim 13, actual 18), the fixtures that are supposed to test the tool's hardest cases (split-direction tariff impact, second-order beneficiaries, competitor read-throughs) have no machine-checkable assertions for the exact thing they claim to test, three of the seven fixture-covered source types have zero real captured fixtures (10-Q, 10-K, GlobeNewswire Earnings), the `source-seed.ts` shape is missing a field the stated Step-2 `sources` table needs to persist (`storeBody`) while carrying two fields the schema has no column for (`verified`, `notes`), `npm run test` is presented in the README as already meaningful but currently exits 1 with zero test files, and a doc comment points at a `docs/evals.md` that does not exist. None of these are blockers to proceeding to CP1, but the volume/cost math is worth doing now: Form 4 alone is a high-volume source, three overlapping GlobeNewswire feeds all get triaged, and the $2/day Stage-B (Opus) budget is likely to be tight to unrealistic once live scanning starts — this is flagged for CP3/CP4 attention now while it's cheap to plan for.

## 1. Secrets and leakage

No hardcoded secrets found anywhere in the tracked tree. Specifically:

- Grepped the whole repo (excluding `node_modules`/`package-lock.json`) for `sk-…`, `ghp_…`, `AKIA…`, `api_key=`, and `Bearer <token>` patterns — zero matches.
- Grepped for `NEXT_PUBLIC_` across `.ts`/`.tsx` — zero matches, confirming the README's claim that no secret is client-exposed (moot today since there's no app code yet, but the config file already only deals in server-side values).
- `.env.example` (`.env.example:11-53`) contains exactly the 10 documented variables, every value empty or a placeholder/non-secret default (`MARKET_DATA_PROVIDER=finnhub`, `DAILY_LLM_BUDGET_USD=2.00`, `APP_URL=http://localhost:3000`, `SEC_USER_AGENT=SignalDesk/1.0 (you@example.com)`). No live credential-shaped value anywhere.
- **Concretely tested** `.gitignore` behavior rather than just reading it: created a real `.env.local` with a fake key, ran `git check-ignore -v .env.local` → matched `.gitignore:34:.env*` (confirmed ignored), confirmed `git status --porcelain` shows nothing for it, then deleted it. `git ls-files | grep -i env` shows only `.env.example` is tracked — the negation pattern at `.gitignore:36` (`!.env.example`) works as intended.
- `git log --all --full-history -- .env.local` returns nothing — no `.env.local` has ever existed in history, in this commit or the initial `create-next-app` commit.
- Repo has exactly two commits (`a54a092` initial scaffold, `b0f2e43` CP0); `git status` is clean.

Nothing wrong in this dimension.

## 4. Fixture quality

- **Counts**: Verified programmatically. 20 items total; 11 marked `synthetic: false` (fx-001…fx-011), 9 marked `synthetic: true` (fx-012…fx-020) — this matches the README/commit message's "11 real, 9 authored" claim exactly, and the `synthetic` flag is set correctly and consistently (no item has a missing or contradictory flag).
- **Real-item consistency against `fixtures/raw/`**: Manually cross-checked every one of the 11 real items against its source raw file — accession numbers, filing sizes, timestamps (with correct UTC conversion from the Atom feed's `-04:00` offset), URLs, and titles all match byte-for-byte between `items.json` and the corresponding `fixtures/raw/*` entry (e.g. `fx-001`/`fx-002`'s VIASAT 8-K, `fx-003`'s PDS Biotechnology 8-K, `fx-004`'s Nuveen Farmland REIT 8-K, `fx-005`–`fx-009`'s five GlobeNewswire items, `fx-010`'s Federal Register NPR-A notice, `fx-011`'s Fed Reserve enforcement-termination notice). No fabricated or mismatched "real" item found.
- **`expected` block testability**: Mixed. Of the 18 items carrying an `expected` block (see MAJOR finding above re: the miscounted "13"), roughly 14 have at least one structurally-testable field (`symbols`, `eventType`, `direction`, `magnitudeMin`, `confidenceMax`, or `dedupeAgainst`). But the four fixtures explicitly billed as the interesting "second-order reasoning" tests — the tariff split (`fx-013`), the data-center beneficiary (`fx-014`), the FDA-CRL competitor read-through (`fx-016`), and the M&A acquirer/peer re-rating (`fx-017`) — encode exactly the part of the claim that makes them interesting only as free-text `note`, with no field an eval harness could assert against. That's the main quality gap in this fixture set (see MAJOR finding).
- **False-positive guard for immaterial news**: Yes — this is well covered. `fx-007` (Verizon hurricane charge waiver — mentions a large-cap ticker but is immaterial), `fx-009` (Oslo-listed Kaldvik — genuinely material but out-of-universe, testing that triage drops on exchange not materiality), `fx-011` (routine Fed enforcement termination against a private bank), `fx-004` (non-traded REIT 8-K), and `fx-018` (routine 10b5-1 vesting Form 4) all specifically target false-positive suppression, each with a distinct failure mode (immateriality, wrong exchange, routine/boilerplate, non-tradable issuer). This is a genuine strength of the fixture design.
- **Sufficiency for building Steps 1-4 without network**: Partially. Coverage is strong for EDGAR 8-K, GlobeNewswire (general + M&A), Federal Register, Federal Reserve, and Form 4 — but as noted in the MAJOR finding above, EDGAR 10-Q, EDGAR 10-K, and the GlobeNewswire Earnings Releases feed have zero fixture items (real or synthetic), despite all three being enabled sources in `source-seed.ts`. A scanner/parser built purely against these fixtures cannot exercise those three source adapters at all.

## 5. Forward-compatibility risks

- **Schema shape mismatch**: covered in the MAJOR finding above — `storeBody` has no destination in the stated `sources` table; `verified`/`notes` exist in the seed with no column to land in either. Worth resolving before CP2's migration is written, since it's a one-line schema decision now vs. a migration-plus-backfill later.
- **No stable identifier for idempotent seeding**: the seed array has no `id`/slug field. When CP2 writes the seeder, it will need *some* stable key to upsert against re-runs (name is a plausible candidate but is free text and already includes punctuation like " - "). Not a blocker, just worth deciding the upsert key now.
- **GlobeNewswire non-English/non-US volume and Stage-A cost**: `source-seed.ts:94-126` runs three overlapping GlobeNewswire feeds (Public Companies, Earnings Releases, M&A) at a 60-second poll interval each, and the file's own comments acknowledge the feed "carries non-English releases (Nordic issuers)" that "Triage drops... after" the fact — i.e., every item, including non-US Danish/Norwegian insider notices, still gets a Stage-A Haiku call before being dropped. Combined with SEC Form 4 (also very high volume — insider filings run into the hundreds to low thousands per day across all US reporting companies) polled every 5 minutes, a rough back-of-envelope for Stage-A item volume once live is in the **low thousands of items/day** (very roughly: ~150-300 EDGAR 8-Ks, an unbounded-but-likely-4-figure count of Form 4s, 300-500 GlobeNewswire items after overlap/dedup, ~100 Federal Register documents, a handful of Fed Reserve releases, plus whatever volume Finnhub's aggregated news feed contributes). At Haiku 4.5 pricing ($1/$5 per MTok) triage itself is cheap per item (a fraction of a cent), so Stage A alone is unlikely to blow the budget. The real risk is **Stage B**: if even 5-10% of a few-thousand-item day survives triage, that's 100-300+ Opus 5 calls/day at $5/$25 per MTok — a single Opus 5 call with a few hundred input tokens and a structured-JSON response with rationale can easily cost several cents, putting a realistic daily Stage-B bill in the **several-dollars-to-low-tens-of-dollars** range on a busy day (earnings season, Form 4 cluster-buy days, etc.). The **$2.00/day `DAILY_LLM_BUDGET_USD` default is likely to be tight-to-unrealistic** once live scanning starts, especially before per-source rate limiting or a Form-4 pre-filter (e.g., skip routine 10b5-1 vesting before even Stage A) is added. This isn't a CP0 defect — PROGRESS.md already flags the $2/day figure as provisional and promises to revisit it at CP4 with real measured spend — but it's worth flagging now given how central Form 4 and the tripled GlobeNewswire polling are to the source list, so the CP3/CP4 design can plan for a pre-Stage-A volume filter rather than relying on the budget breaker to catch it after the fact.

## 6. Cost and safety risks

- **Content storage rule** (title+summary+link for news, full body only for government/wire sources) is followed correctly and consistently in `source-seed.ts`: all `rss`/`api` government and wire sources (EDGAR, Federal Register, Federal Reserve, GlobeNewswire) have `storeBody: true`; the one aggregated-news source (Finnhub) has `storeBody: false` with an explicit comment ("we never store third-party article bodies"). No violation found.
- **SSRF surface**: README explicitly states "Feed URLs come only from the server-side config, never from user input" (`README.md:188-189`), and at CP0 this is true by construction — there is no code yet that accepts a URL from any external input, and the seed list is a static, hardcoded array. This claim will need to be re-verified once the `/sources` admin page (mentioned as a Step 3+ feature) is built, since that's presumably where an admin could add a new source URL — worth a callback in a future review once that UI exists, but it's not a CP0 issue today.
- **Runaway LLM spend**: see §5 above — the main concrete risk visible at CP0 is the combination of high Form 4 volume, triple-polled overlapping GlobeNewswire feeds, and a low default budget, rather than any code-level bug (there is no scanning/scoring code yet to have a bug in).
- **Legal/ToS**: the seed's own comments show the author already made a defensible call here — Business Wire and PR Newswire ship disabled after returning 403 to a probe rather than being force-enabled with a spoofed User-Agent, and the "no HTML scraping of paywalled or scrape-prohibiting sites — feeds and official APIs only" rule (`source-seed.ts:16`) is consistent with every entry in the list (all are RSS feeds or official APIs, no scrapers).
